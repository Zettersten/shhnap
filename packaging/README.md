# Distribution runbook

Shnapp is a Windows 11 desktop app. The source project remains at version `0.1.0` during development. A stable tag such as `v1.0.0` supplies the portable assembly version `1.0.0` and the Store MSIX version `1.0.0.0`. The workflow rejects prerelease tags and does not publish a release on a tag push.

## Before the first public tag

1. Test x64 on a real Windows 11 device: capture, annotate, save, share, background startup, upgrade, and uninstall. Check both ZIPs extract with `Shnapp.exe`, `Shnapp.pri`, `LICENSE`, and `THIRD_PARTY_NOTICES.txt` at their roots. CI cross-publishes ARM64 but cannot run it on ARM64 hardware; record this limitation in release notes until an ARM64 device is available.
2. Review the MIT license and first-party artwork; inspect the bundled `THIRD_PARTY_NOTICES` directory against the exact .NET runtime and NuGet packages. The notice collector copies package license and notice files; Win2D's NuGet metadata points to an obsolete license URL, so it includes the [official Win2D source MIT license](https://github.com/microsoft/Win2D/blob/winappsdk/main/LICENSE.txt) and flags a package-terms review. [.NET's licensing guidance](https://github.com/dotnet/core/blob/main/license-information.md) explains that self-contained apps embed .NET runtime parts. Publish `https://shhnap.com/privacy`; check the support and issue forms; enable GitHub private vulnerability reporting; audit repository history before changing repository visibility. Test Windows Defender/SmartScreen behavior for the unsigned portable build and decide whether to sign direct downloads. [Microsoft's code-signing options](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options) describe the tradeoffs.
3. Verify the website's release availability source before publishing. Keep catalog links hidden until their submissions are accepted.
4. **Defer the Store submission for the first tag** because Partner Center identity values are not available yet. Enroll in Partner Center, reserve the public **Shnapp** name, and copy the exact `Package/Identity/Name`, `Package/Identity/Publisher`, and `Package/Properties/PublisherDisplayName` values from [Product identity](https://learn.microsoft.com/en-us/windows/apps/publish/view-app-identity-details). Set repository variables `STORE_IDENTITY_NAME`, `STORE_IDENTITY_PUBLISHER`, and `STORE_PUBLISHER_DISPLAY_NAME` to those values. The source manifest deliberately has a development identity; **Shnapp is the display name, not a guaranteed technical package identity**. Use the ready-to-edit [Partner Center listing draft](store/LISTING-DRAFT.md), then verify its privacy, screenshots, and capabilities against the final build. The MSIX can be built later from the first tag using the manual `build-store-msix` workflow operation.

## Stage, review, and publish a GitHub release

1. Create and push the reviewed stable tag, starting with `v1.0.0`. The tag run tests x64, produces self-contained x64 and ARM64 portable ZIPs, computes SHA-256 sidecars, then creates a **draft** release. It re-downloads the draft's assets and checks every byte. Existing release assets are never overwritten.
2. Review the Actions run and draft release. The release must contain exactly `Shnapp-win-x64.zip`, `Shnapp-win-x64.zip.sha256`, `Shnapp-win-arm64.zip`, and `Shnapp-win-arm64.zip.sha256`. Test the x64 archive on Windows 11, validate the ARM64 archive structurally, review/edit the release notes with the ARM64 hardware-test status, and download the `Catalog-candidates-v1.0.0` Actions artifact for catalog submission. If a future Store job runs, download each unsigned MSIX and `.msixupload` Actions artifact and validate it before submission.
3. In **Actions → Windows build and release → Run workflow**, select `publish-github-release` and enter the exact tag. This dispatch re-downloads and verifies the draft release, then publishes it. There is no automatic publication on tag push.
4. Once the release is public, enable the version's direct download on the site. A stable ZIP name permits `https://github.com/Zettersten/shhnap/releases/latest/download/Shnapp-win-x64.zip` for visitors; catalog manifests use immutable versioned URLs such as `https://github.com/Zettersten/shhnap/releases/download/v1.0.0/Shnapp-win-x64.zip`. Enable [GitHub immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases) in repository settings before publication if available for the repository; the workflow itself only prevents its own overwrites.

If staging fails after creating a draft, inspect that draft and the Actions log. The workflow refuses to clobber an existing draft. Resolve the failure before publishing; do not silently replace a published ZIP, because WinGet, Scoop, and Chocolatey pin hashes.

## Submit catalog candidates after publication

`packaging/release/New-CatalogPackages.ps1` reads both ZIPs and their checksum files, verifies the hashes and ZIP root files, then renders versioned **WinGet**, **Scoop**, and **Chocolatey** candidates from the `.in` templates. The tag workflow runs it on the downloaded draft assets. To rerun locally:

```powershell
./packaging/release/New-CatalogPackages.ps1 -ReleaseTag v1.0.0 -AssetsDirectory ./release-assets -OutputDirectory ./artifacts/catalog/v1.0.0
```

- **WinGet:** Confirm `Zettersten.Shnapp` is available, run `winget validate` on the generated version directory, and install from that manifest on x64; test ARM64 when hardware is available. Fork [microsoft/winget-pkgs](https://learn.microsoft.com/en-us/windows/package-manager/package/repository), place the three generated YAML manifests in the generated `manifests/z/Zettersten/Shnapp/<version>` path, run its `Tools/SandboxTest.ps1`, then open a single-package PR. Microsoft's automated install and security checks and possible moderator review are the acceptance gate. The ZIP uses WinGet's `NestedInstallerType: portable` with `Shnapp.exe` at ZIP root. `ArchiveBinariesDependOnPath: true` keeps execution in the extracted folder so its adjacent .NET and Windows App SDK DLLs remain available ([manifest field](https://github.com/microsoft/winget-pkgs/blob/master/doc/manifest/schema/1.28.0/installer.md#archivebinariesdependonpath---optional-indication-to-add-the-install-location-directly-to-path-only-applies-to-an-archive-containing-portable-packages)). Update the manifest and checksum for every new published version; the catalog does not update itself from a GitHub release.
- **Scoop:** The fastest controllable path is a public owner-maintained bucket created from [Scoop's BucketTemplate](https://github.com/ScoopInstaller/Scoop/wiki/Buckets). Commit the generated `scoop/bucket/shnapp.json` to `Zettersten/scoop-bucket`, then users can run `scoop bucket add shnapp https://github.com/Zettersten/scoop-bucket`. Validate the manifest with Scoop's `checkver.ps1`, then install and upgrade from the bucket. Scoop Extras is the appropriate shared bucket for a GUI app, but its [contribution guide](https://github.com/ScoopInstaller/.github/blob/main/.github/CONTRIBUTING.md) asks for an issue and maintainer approval before a new-package PR; use that route after the owner bucket works. Its `checkver` and `autoupdate` fields point to stable GitHub releases and adjacent SHA-256 files, but the bucket still needs a committed update. See [Scoop manifest autoupdate](https://github.com/ScoopInstaller/Scoop/wiki/App-Manifest-Autoupdate).
- **Chocolatey:** The `publish-github-release` dispatch now starts a downstream `Pack and test Chocolatey` job after the GitHub release becomes public. It downloads the immutable release ZIPs and checksums, regenerates the package from those exact bytes, runs `choco pack`, installs from the local `.nupkg` on a clean Windows Server 2025 runner, checks the extracted files, uninstalls, and uploads the tested package as an Actions artifact. Use the `verify-chocolatey` dispatch for an existing public tag such as `v1.0.0`; this is needed for the first release because it was published before this job existed. Hosted Server 2025 checks the package mechanics but does not replace Windows 11 GUI testing. The install script rejects Windows builds before 22000, verifies the downloaded ZIP's SHA-256, and keeps all self-contained files together. Test ARM64 when hardware is available.

  To submit, [register and verify a Chocolatey Community account](https://docs.chocolatey.org/en-us/create/commands/api-key/), confirm the `shnapp` package ID is available, and place a newly generated API key in the repository's **Actions secret** named `CHOCOLATEY_API_KEY`. Never commit or paste the key into an issue, workflow file, or chat. In **Actions → Windows build and release → Run workflow**, select `publish-chocolatey` and enter the same stable release tag. That operation repeats the package verification, then a separate job downloads the tested `.nupkg` artifact and runs [`choco push`](https://docs.chocolatey.org/en-us/create/commands/push/) using the secret. `publish-github-release` verifies the Chocolatey package automatically but does not submit it; a new package version requires its own `publish-chocolatey` dispatch. [Community moderation](https://docs.chocolatey.org/en-us/community-repository/moderation/) must approve each version before it is visible. [Chocolatey's verifier uses Windows Server 2019](https://docs.chocolatey.org/en-us/community-repository/moderation/package-verifier/), where this Windows 11-only package correctly fails; request a verifier exception from moderators if needed.
- **Microsoft Store:** This project uses a separate single-project MSIX build, not a ZIP or EXE installer submission. The CI job is gated by Partner Center identity variables and produces unsigned, architecture-specific `.msix` and `.msixupload` Actions artifacts for manual review. Prefer submitting the two `.msixupload` files because each includes its architecture's MSIX and public symbols for Store crash analytics; [Partner Center accepts `.msix`, `.msixupload`, and bundles](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/msix/upload-app-packages). If identity arrives after the first tag, use the workflow's `build-store-msix` operation with that existing tag. Run the Windows App Certification Kit, test install/update/startup, and explicitly test migration or import of a library created by the portable build before submitting: packaged desktop app writes to AppData can be [redirected to a private per-package location](https://learn.microsoft.com/en-us/windows/msix/desktop/desktop-to-uwp-behind-the-scenes). The Store re-signs MSIX submissions; a directly distributed/sideloaded MSIX needs your own signing certificate. Single-project MSIX emits separate architecture packages rather than an MSIX bundle; upload files only if Partner Center accepts the chosen shape and version. See [single-project MSIX](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/single-project-msix), [MSIX requirements](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/msix/app-package-requirements), and [WinUI CI](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/ci-for-winui3). Store account access, exact identity, certification, and listing approval are external blockers.

For each new stable version, repeat the tag and draft review, publish the GitHub release, then update and submit each catalog separately. Update the website's availability state only after each catalog accepts the version.
